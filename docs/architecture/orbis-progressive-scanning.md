# Progressive Orbis scanning

Orbis uses the optimized progressive scanner and persistent exact indexes by default. Set `ORBIS_DISABLE_INCREMENTAL_SCAN=1` to force full progressive refreshes. `ORBIS_LEGACY_SCAN` is retained as a no-op compatibility variable, so commands that set it still receive live previews, saved pause/resume, persistent indexes, focus/reveal, and incremental refresh. The Stage 5 reference scanner is benchmark-only. `ORBIS_PROGRESSIVE_SCAN` is no longer read.

The progressive scanner keeps its construction database private to the worker and performs exact read-only filesystem traversal. It does not query Spotlight or maintain a live watcher. Full scans use bounded `DELETE`-journal transactions with `synchronous=FULL`. `scan-resume.json` names one owned partial database and candidate. The database's `scan_run` row holds mutable state, including the node-ID seed, phase, checkpoint sequence, active elapsed time, and original FSEvents baseline. After a completed scan, the controller writes the root's exact direct-child totals to a private, volume-identity-bound cache. The next rescan or app launch applies that cache before traversal starts, so folders such as `Users` and `Applications` retain one pinned provisional value until their new exact totals are ready. Cache values are construction-only and never enter published exact totals. A first-ever scan with no cache shows the currently confirmed bytes as a known partial size and updates it as traversal progresses. When previews are enabled, exact traversal reads 32 root entries once and publishes that batch before another metadata read or descendant open. Later reads use 256 entries. Both Node and native adapters cap a requested page at 1,024 entries. Node metadata reads still run at four operations by default, and traversal keeps at most eight directory handles open. On macOS the optional Rust/N-API addon returns one packed `ORB1` version-1 buffer per page instead of one N-API object per entry. After preflight it opens one metadata tree anchored to the canonical target descriptor. Every relative path component is opened with `openat`, `O_DIRECTORY`, and `O_NOFOLLOW`. Failed, malformed, or unavailable native pages close that cursor and replay from the persisted entry cursor through bounded Node metadata reads. Normal work is breadth-first. Focused work gets three turns before one normal turn, so opening a folder makes its known subtree responsive without stopping the rest of the scan.

The estimate cache is an app-private `0600` file. It contains the canonical target, volume identity, capture time, and up to 400 direct-child names and byte totals; it expires after 30 days and is never sent to the renderer as a path-bearing payload. In suite mode, an interrupted scan reopens its construction database read-only and displays the last durable path-free preview while waiting for the user to click Resume. Startup does not create a scan worker or continue filesystem traversal. After Resume, the controller publishes a path-free `resuming` snapshot before starting the worker. The saved chart, focus, breadcrumbs, largest items, and volume stay visible while preparation moves through validation, FSEvents history, interrupted-directory recovery, repair, and traversal startup. Worker generation, request, and phase-order checks reject stale or regressive updates. The first scanner progress replaces preparation with normal traversal. If startup or recovery fails, the controller keeps the durable-at-start preview visible while authoritative resume loading decides whether to return to paused-with-resume or remove the stale construction preview. A previous published index remains available in either case. The worker sends an initial path-free preview after the first root page, including a root page made entirely of skipped or unreadable entries. Later previews are limited to 10 Hz. A preview contains opaque node IDs, display names, changing aggregate values, at most 400 chart segments, and at most 100 largest items. The chart builder keeps the largest visible directories and files, folds files below a 1% parent-size share or over-limit siblings into a single `Other` segment, and includes its represented item count without changing byte totals. At the startup-disk root, segment percentages and angles use total disk capacity as their denominator; free and otherwise unrepresented capacity remains a blank arc. Folder-level charts continue to fill the full circle relative to the selected folder. Filesystem paths stay in the worker and the main process's private index.

The construction database applies each metadata batch in one synchronous SQLite savepoint. File nodes, tracked hard-link paths, and final hard-link owners are inserted through SQLite JSON rowsets; ancestor, direct-child, and observation deltas are coalesced by parent. Progress-only page completions use the leased task path and do not query SQLite, so they do not flush pending metadata. A real preview, focus query, checkpoint, pause, or finalization still flushes the batch first. Cache mutations are restored if the savepoint rolls back. Node and observation writes, hard-link ownership, task cursor and queue changes, revision changes, and metadata counters either all release or all roll back. `entries_read` advances only after every entry in the batch has been processed, and previews run after the savepoint releases. Cancellation remains checked for each entry. On resume, the scheduler captures an affected recovery set in connection-local temporary tables, keeps completed directory work, and resets the highest incomplete directories. It deletes children and tracked hard-link paths discovered by those incomplete enumerations and reads each directory again from its beginning because directory ordering is not stable across handles. Hard-link identities and old duplicate-observation contributions are captured before deletion; only those identities are repaired in UTF-8 binary path order, while unaffected owner, path, and observation rows remain untouched. Focus transfers from a deleted task to its retained recovery root. Each task persists `ready`, `pending_children`, `subtree_complete`, and a shallow-depth scheduling band. Scheduler fields and directory aggregates are recomputed only for recovery roots, their ancestors, and surviving owner-parent chains. Aggregate rows use a bottom-up direct-child equation, so unrelated directories are not rewritten. A scoped equation mismatch may use one guarded recursive rebuild as a diagnostic fallback; it rejects unrelated aggregate corruption and records the fallback separately. A traversal-phase construction containing finalized `hardlink_groups` is treated as invalid resumable state and takes the existing fresh-scan retry; ordinary recovery errors abort without discarding the durable checkpoint. Finishing enumeration releases direct children. An iterative parent walk settles a directory only after its own enumeration and all child subtrees finish. `takeWork()` uses one focused and one normal prepared query, then merges both lists with the three-focused-turn rule. Descendant tasks cannot run until their parent enumeration is terminal, even after a focus change. The persisted HMAC seed keeps node IDs stable. Recovery derives semantic totals from nodes and direct observations, so replay cannot inflate totals. Nodes expose confirmed bytes separately from an estimate-aware display size and report `estimated`, `partial`, or `exact` accuracy. Hard-link ownership uses the relative path as a deterministic tie-breaker, so focus order cannot change the final allocated-byte total or representative. Before publication, the scanner rejects queued work, removes its scheduling, hard-link, and estimate tables, commits, closes the database, and atomically renames it.

## Persistent refreshes

Completed progressive indexes use schema 3. Unique files live only in `nodes`. `hardlink_paths` stores every observed path only for identities whose link count is not exactly one, and `hardlink_groups` records one UTF-8 binary-minimum owner for each tracked identity. Direct directory observations retain skipped-entry semantics. Schema-2 publications and schema-1 or schema-2 saved constructions are never migrated in place. Orbis leaves the old publication untouched and completes a new full scan before schema-3 data becomes current. `indexes/current.json` identifies one immutable `index-<uuid>.sqlite` publication and stores the target device/inode, schema and policy versions, revision, FSEvents UUID, and decimal-string cursor. Startup trusts only that manifest and its validated database. Recognized partial files and unreferenced index candidates are removed; unrelated files are never touched. Cleanup also reads a valid resume descriptor and preserves its partial or finalized candidate plus recognized SQLite journal files. Normal shutdown pauses full construction, closes its database, and preserves the manifest, active index, estimate cache, and saved construction.

On macOS, the worker replays bounded FSEvents history from the published cursor. Events only select dirty paths. The worker clones the active index, recursively traverses conservative scopes with the same exact progressive scanner, replaces those subtrees in one SQLite transaction, repairs only hard-link identities removed from or inserted by those scopes, repairs aggregates bottom-up, and validates foreign keys, aggregate equations, and owner allocation. A changed target identity, journal UUID mismatch, dropped or wrapped events, root or mount changes, malformed history, ambiguous rename, timeout, event limit, or candidate validation failure triggers a full progressive scan. `MustScanSubDirs` expands the exact reconciliation scope without deriving byte deltas from events.

A full refresh captures and durably records a pre-traversal journal checkpoint before enumeration. Resume keeps that baseline rather than capturing a replacement. During long scans, the worker drains bounded history about every 30 seconds. It commits coalesced dirty scopes and the private drained-through cursor in the same checkpoint transaction; this cursor never updates `current.json`. Traversal checks checkpoint cadence after each released batch and unreadable-directory result. A due checkpoint needs five seconds since the previous checkpoint, 32,768 successfully processed entries, or the journal-drain timer. The first preview, ordinary page completion, and directory completion do not force a checkpoint. Initial resumable setup, pause or error preservation, and both finalization transitions still force a commit. The final journal drain is included in the first finalization commit instead of causing a separate checkpoint. Every successful construction commit reports its reason and sequence. The first `resume-invalidated` failure discards that construction and retries without resumability; the same refresh request does not create another resumable construction. Before reopening saved work, Orbis verifies the target device/inode, index-directory identity, schema and policy versions, and owned regular files. Startup, crash, timeout, and unacknowledged paths run the authoritative SQLite integrity and foreign-key checks. A same-process receipt can skip those two checks only after the store matches the exact descriptor digest, checkpoint row, database stamp, and WAL/SHM sidecars before and after its read. A clean acknowledged Pause uses the same cheap checkpoint proof without a second integrity pass. Any receipt mismatch falls back to authoritative validation. Receipts stay in memory, cross only to the worker, and are consumed once. A target replacement or untrustworthy history discards construction and starts fresh. A disconnected target preserves both the last publication and saved construction until it reconnects. At traversal completion, the worker replays through a post-scan fence. If bounded subtree reconciliation closes that window, the applied fence is published with the candidate. If FSEvents is unavailable before traversal, the exact full index may publish without a cursor and later refreshes remain full. If a captured window is still untrustworthy after one bounded full retry, the candidate is discarded and the previous publication remains authoritative. A batch with no relevant events atomically advances only `current.json` and retains the same index file.

Publication fsyncs and renames the candidate, validates it read-only, then fsyncs and renames `current.json`; the manifest rename is the commit point. A finalized candidate remains descriptor-owned until the controller publishes that manifest. If the process stops between the two renames, startup validates the candidate and retries publication. Only the controller clears the descriptor, and only after `current.json` commits. The cursor never advances beyond the manifest's index. The UI calls full-scan cancellation Pause. The worker closes directory handles, rolls back uncommitted work, and acknowledges the last durable checkpoint before termination. A timeout or unexpected exit still preserves the previous checkpoint. `cancelScan()` remains a compatibility alias for Pause. "Discard saved scan" removes descriptor-owned construction files only and leaves the previous index and cursor authoritative. Incremental candidates remain disposable. A disconnected target remains displayable from the prior index and reports refresh failure.

During a refresh, the controller keeps the previous completed `DiskIndex` open. Full scans show a provisional snapshot only after a preview arrives; incremental candidates do not expose geometry before commit. The new database replaces the old one only after it opens and validates successfully. A stale generation cannot complete a pending reveal or replace the active index.

Snapshot version 3 adds `resuming` to the progress-stage vocabulary without changing the snapshot version or public IPC methods. Preparation uses fixed messages and a minimum progress-bar value rather than deriving a percentage from saved counts. Snapshot version 3 marks provisional data with `committed: false` and published data with `committed: true`. Its optional path-free `scan.resume` field reports saved progress and checkpoint time. The compatible `canceled` status renders as "Scan paused — progress saved" when resume is available. Standalone starts the saved scan after launch; suite mode reports it and waits for an explicit Resume. Nodes, chart segments, and volumes carry `sizeAccuracy`; this prevents an estimated or partial byte count from being presented as exact. Directory nodes report `queued`, `scanning`, `complete`, or `unreadable`. Queued and scanning chart segments use crossed hatching and remain drillable even when their known size is zero. The preload bridge rejects older or structurally incomplete snapshots.

## Performance checks

Run matched benchmark samples at metadata concurrency 4. The harness can still select the independent Stage 5 reference with `--scanner legacy`, but its output lacks the progressive alias and construction schema and is not a production rollback.

Useful controls are `ORBIS_SCAN_DIAGNOSTICS=1`, `ORBIS_DISABLE_BULK_METADATA=1`, and `ORBIS_DISABLE_INCREMENTAL_SCAN=1`. `ORBIS_DISABLE_BULK_METADATA=1` affects only directory metadata acceleration and does not disable FSEvents. Native build and staging are wired through `apps/Orbis/native:mac`, `pnpm features:stage`, and the `features/orbis/native` packaged resource.

The reports in `../benchmarks/orbis-progressive-rollout.md`, `../benchmarks/orbis-progressive-batching.md`, and `../benchmarks/orbis-featureful-fast-default.md` record the rollout, attempted optimizations, reverted experiments, and final decision. The retained optimization roughly doubled warm-fixture progressive throughput. It did not reproduce the non-feature-equivalent Stage 5 60k–74k items/s figures.
